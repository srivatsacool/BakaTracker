# AI Architecture — Workers AI + BakaSur foundation (v2.1)

## Target architecture

```
                         BAKASUR
                            │
                            ▼
                     Worker AI Service
                            │
                    ┌───────┴────────┐
                    ▼                ▼
               Workers AI       Application Tools
                    │                │
             ┌──────┼─────┐     ┌───┼──────────┐
             ▼      ▼     ▼     ▼   ▼    ▼      ▼
            LLM   Embed  ASR   D1  R2  Notes   Tasks
                           TTS       │
                                     ▼
                                  Vectorize
                                     │
                                  Memory
```

Scope of THIS phase (bold): **Worker AI Service (LLM + embeddings only)**,
the **Notes summarize vertical slice**, the **BakaSur tool contract**, and the
**proactive BakaSur scheduled engine** (deterministic candidates → policy →
AI message → delivery abstraction; the delivery transport itself is NOT
built — see `docs/ai/notifications.md`).
ASR/TTS/vision, the agent loop, and Vectorize are designed but not built.

## Layer rules (non-negotiable)

1. **D1/R2 remain the source of truth.** AI performs inference only.
2. **BakaSur never receives direct DB access.** Every data access goes
   through the Tool Registry → Repository → SQL/R2 chain with the
   authenticated `ToolContext.user.sub` — the exact same path REST and MCP
   use. This invariant already exists; the AI layer adds nothing parallel.
3. **Tool calls pass through existing auth + authorization + business
   logic.** The registry is the only funnel (`registry.call(name, input,
   ctx)`), zod-validating every argument.
4. **AI is user-scoped.** `ctx.user.sub` (from the bearer token) scopes
   every repository call; prompts carry no other user's data; Vectorize
   (future) is filtered by `user_id` metadata.
5. **No raw SQL generated by the model.** SQL lives only in
   `storage/db.ts`, called by repositories, called by tools. The model
   never emits queries — it emits tool-call arguments that are schema-
   validated.
6. **No model-generated arbitrary Worker execution.** The model can only
   request registered tools with bounded, validated arguments.
7. **Failures degrade gracefully.** No AI binding / flag off → deterministic
   `503 ai_unavailable`. Upstream failure → `502`. Core CRUD/sync/files
   never depend on the AI service.

## Layer stack

```
REST action route (POST /api/v1/notes/:id/ai/summarize)
        │  (auth guard already applied)
        ▼
AiService  (src/ai/service.ts)          ← the mockable application boundary
        │  generateStructured / generateText / generateEmbedding
        ▼
AIProvider  (src/ai/provider.ts)        ← transport abstraction (existing)
        │  chat() / embed()
        ▼
Workers AI binding (env.AI)  |  Gemini REST (fallback, GEMINI_API_KEY)
```

- **Provider** (`AIProvider`) = transport. Already exists; extended with an
  optional `model` identifier and an `embed()` capability.
- **Service** (`AiService`) = application contract: bounded input
  (`AI_INPUT_MAX_CHARS = 24_000`), bounded output (maxTokens + hard caps),
  zod-validated structured results (JSON extraction + fail-closed schema
  checks), request ids, deterministic error taxonomy
  (`ai_unavailable | ai_input_too_large | ai_upstream | ai_output_invalid |
  ai_not_supported`), secret-safe logging (ids + counts only, never content).
  Business logic (routes/tools/engine) talks to the service, never to
  `env.AI` directly.
- **Mock boundary**: tests inject a fake `AiService` (or fake provider) into
  the REST app builder (`buildRestApp({ aiService })`) and the notification
  engine (`runNotificationEvaluation({ ai })`). No live model inference in
  tests.

## Model configuration

Verified available on this account (2026-08-11, `wrangler ai models list`):

| Purpose | Model (default) | Notes |
|---|---|---|
| Text generation | `@cf/meta/llama-3.3-70b-instruct-fp8-fast` | overridable via `AI_MODEL` |
| Embeddings (future) | `@cf/baai/bge-base-en-v1.5` (768-d) | for Vectorize; also `bge-small-en-v1.5` (384-d), `qwen3-embedding-0.6b` |

Config knobs (all optional, all default-safe):

- `AI` binding — presence enables the provider (prod config only; local dev
  intentionally omits it → deterministic 503 in dev).
- `AI_MODEL` (var) — override the text-generation model name.
- `AI_EMBED_MODEL` (var) — override the embedding model (Vectorize future).
- `AI_ENABLED` (var, default `"1"`) — kill switch; `"0"` disables AI even
  with the binding present.
- `GEMINI_API_KEY` (secret) — documented alternative provider.

## What is deliberately NOT in this phase

- **Vectorize**: no production index; design only (`docs/ai/memory-vectorize.md`).
- **AI Gateway**: no concrete reason yet (no caching/fallback/analytics
  requirement in the slice); revisit when the agent loop lands.
- **Agent loop**: BakaSur tool *calls* are designed and allowlisted; the
  model is not yet given a loop. The summarize slice is a direct service
  call — no tools in the loop.
- **Notification delivery transport**: the proactive engine evaluates,
  generates, and delivers through a `LogDelivery` stub; Web Push/email are
  NOT built (`docs/ai/notifications.md`).
- ASR/TTS/vision, image generation, PDF intelligence, autonomous mutation.

## Proactive BakaSur (scheduled)

The Worker now has a `scheduled` handler (Cron `*/15 * * * *`) that runs the
deterministic notification engine:

```
scheduler (WHEN) → active users → deterministic candidates (WHETHER)
  → policy suppression (SAFETY) → Workers AI message (HOW) → delivery (WHERE)
```

The model decides NOTHING about whether or when a notification fires — it
only phrases it, inside a 280-char zod-validated envelope, from a bounded
fact context. Full design: `docs/ai/notifications.md`.
